\begin{abstract}
The digitization of public administration requires intelligent systems that can guide citizens through complex, multi-step regulatory workflows while remaining reliable under the integration faults that characterize real production environments. This paper makes two contributions. First, we present a multi-agent architecture for Romanian tax administration built with the UiPath Python SDK and LangGraph, comprising an intent-routing orchestration layer, five domain-specific agents covering PFA contributions, property sale tax, rental income, fiscal certificates, and electronic invoicing, and a shared services tier integrating retrieval-augmented generation, deterministic tax computation, document processing, and payment handling. External calls to national platforms, including ANF SPV, Ghiseul.ro, and RO e-Factura, are handled through mocks that replicate the response of each service, allowing the full agent pipeline to be exercised without live government system access. Second, we evaluate system robustness through a controlled fault injection framework that instruments all 19 external service boundary operations with four chaos operators: timeout, delay, partial response, and corruption, at configurable rates with a seeded RNG for reproducibility. Experiments across 100 boundary calls reveal a structural silent pass-through rate of approximately 63\%: faults that do not perturb the downstream branching predicate propagate undetected, with the LLM generating plausible citizen-facing responses despite receiving null or corrupted service data. This finding motivates the addition of output-level contract verification as a necessary complement to agentic systems deployed in regulated public services.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

The digitization of public administration services has become a strategic priority across Europe, with Romania advancing initiatives such as the ANAF Spatiul Privat Virtual (SPV) portal for tax declarations, the Ghiseul.ro platform for electronic payments, and the RO e-Factura system for mandatory electronic invoicing. These platforms, while functional individually, impose a significant burden on citizens and businesses who must navigate multiple interfaces, understand evolving tax regulations, and coordinate across disconnected services to complete routine fiscal obligations. Agentic AI systems, where large language models (LLMs) orchestrate multiple specialized agents to decompose complex tasks, interact with external services, and maintain contextual state across multi-step workflows, offer a promising path toward unified, conversational interfaces that can guide users through these fragmented processes \cite{Pan2025, WEF2025}.

The UiPath Python SDK and its LangChain integration layer (\texttt{uipath-langchain}) provide a purpose-built foundation for constructing such agentic systems within an enterprise automation platform. The SDK exposes programmatic access to the full spectrum of UiPath Orchestrator services: process invocation to trigger attended and unattended robotic workflows, creation of action center tasks for human-in-the-loop escalation, queue management for batch processing of structured work items, storage buckets for document persistence, and Context Grounding for retrieval-augmented generation (RAG) over indexed knowledge bases \cite{LangGraph2025}. The \texttt{UiPathChat} class and the \texttt{ContextGroundingRetriever} enable LangGraph-based agents to leverage the Orchestrator's LLM gateway and vector search infrastructure without managing separate model deployments or embedding pipelines. This tight integration means that a coded agent running as a LangGraph state machine can, within a single execution trace, classify user intent via an LLM call, retrieve relevant articles from the Romanian Tax Code through Context Grounding, compute tax obligations using deterministic calculation services, and invoke mocked boundary adapters for ANAF SPV declaration submission and Ghiseul.ro payment initiation, all coordinated through the UiPath platform's authentication, folder-based access control, and job lifecycle management.

However, deploying such systems in a public administration context introduces reliability requirements that go beyond functional correctness. Citizens interacting with a tax agent expect consistent behavior even when one of the underlying government services is slow, partially unavailable, or returns a malformed payload, conditions that are commonplace in production integrations, but rarely tested explicitly during development. An agent that conditions its behaviour solely on a service-reported status flag may generate plausible-sounding responses despite having received corrupted or incomplete data, silently masking the underlying fault from the citizen. Validating this class of failure requires intentional stress testing at the external service boundaries, akin to the chaos engineering discipline developed for microservice architectures~\cite{Basiri2016}.

In this paper, we present two complementary contributions. First, a multi-agent architecture for Romanian tax administration that implements a hierarchical supervisor topology \cite{AutoGen2023} built on LangGraph's \texttt{StateGraph} with conditional routing: 

\begin{enumerate}
    \item An Entry Agent performs intent detection and routes citizen requests to one of five domain-specific agents (PFA/Freelancer, Property Sale, Rental Income, Certificate, and E-Factura), each supported by shared services for document intake, RAG-based tax code consultation, tax computation, and payment processing. 
    \item A fault injection framework that instruments all 19 external service boundary operations with four chaos operators (timeout, delay, partial response, and corruption) applied at configurable rates with a seeded RNG for reproducibility. We evaluate the system under injection rates from 0\% to 100\% and find that approximately 63\% of injected faults propagate silently through the agent, with the LLM generating coherent citizen-facing responses despite receiving null or corrupted service data.
\end{enumerate}

This structural result, which we show to be independent of the injection rate, motivates the design of an output-level validation layer as a necessary complement to any agentic system deployed in a regulated public service context.


\section{Related Work}
\label{sec:related}

\paragraph{Agentic AI for digital government and tax services}
The application of NLP and AI to public administration has progressed from rule-based document classification toward conversational, multi-step automation. Jiang et al.~\cite{Jiang2023} identify automation, extension, and transformation as the principal contribution patterns across 1{,}032 NLP studies in government settings, while Madan and Ashok~\cite{Madan2022} survey the diffusion barriers to AI adoption in public sector organisations, highlighting transparency and accountability as dominant concerns. In tax administration specifically, Nay et al.~\cite{Nay2024} showed that GPT-4 augmented with RAG over the US Code of Federal Regulations achieves competitive accuracy on thousands of tax law questions, establishing the feasibility of LLM-based fiscal advisory. At the institutional level, Schmitz et al.~\cite{Schmitz2025} identify governance dimensions that agentic AI deployments in public-sector organisations must satisfy before production use. Our work is the first, to our knowledge, to instantiate a complete multi-agent tax service stack on a commercial automation platform covering five Romanian-specific workflows.

\paragraph{Multi-agent architectures and retrieval-augmented generation}
Wang et al.~\cite{Wang2024survey} provide a unified framework for LLM-based autonomous agents decomposed into profile, memory, planning, and action modules. The AutoGen framework~\cite{AutoGen2023} and LangGraph~\cite{LangGraph2025} are complementary instantiations: the former emphasises conversational agent coordination, the latter a typed state-machine substrate suited to stateful, long-running workflows. Our system uses LangGraph's hierarchical supervisor pattern with intent-gated conditional routing. For knowledge grounding, Gao et al.~\cite{Gao2024} survey the RAG paradigm comprehensively; Pipitone and Houir Alami~\cite{Pipitone2024} specialise this to legal text, demonstrating that retrieval precision is the dominant quality factor in regulatory question answering, the same challenge our per-domain Context Grounding indices address.

\paragraph{Robustness, fault injection, and reliability of LLM agents}
AgentBench~\cite{Liu2024AgentBench} benchmarks LLMs as agents across eight environments, identifying long-horizon reasoning and instruction-following as the primary failure modes. Rabanser et al.~\cite{Rabanser2026} propose twelve reliability metrics spanning consistency, perturbation robustness, and predictability, finding that capability gains yield only marginal reliability improvements. Shah et al.~\cite{Shah2026} empirically characterise faults across 40 open-source agentic repositories, identifying boundary failures between probabilistic LLM outputs and deterministic program logic as the dominant class, precisely the failure mode our injection framework targets. The closest prior work to our approach is Owotogbe~\cite{Owotogbe2025}, who applies chaos engineering to LLM multi-agent systems by injecting hallucinations and communication failures; Gupta~\cite{Gupta2026} extends this with ReliabilityBench, covering timeouts, partial responses, and schema drift across 1{,}280 evaluation episodes. Our contribution differs in grounding fault injection in a concrete regulated deployment, implementing a decorator-based injection layer that is architecturally decoupled from agent logic, and deriving a closed-form expression for the silent pass-through rate that motivates output-level contract checking.


\section{Methods}
\label{sec:methods}

This section describes the multi-agent architecture for Romanian tax administration and the fault injection framework used to evaluate its robustness under simulated service failures. The system design is organized into five architectural layers: user interface, orchestration, domain agents, shared services, and infrastructure. An additional fault injection layer instruments the mocked external boundaries, allowing controlled perturbation of service responses during development and testing without requiring live access to government portals.

\subsection{System architecture}
\label{subsec:architecture}

The architecture follows a hierarchical supervisor pattern implemented as a LangGraph \texttt{StateGraph} with typed state, conditional routing, and message aggregation. Figure~\ref{fig:architecture} presents the complete system organization across five layers: user interface, orchestration, domain agents, shared services, and infrastructure.

\begin{figure}[t]
\centering
\includegraphics[width=\columnwidth]{goal_architecture.png}
\caption{Multi-agent architecture for Romanian tax administration. The orchestration layer routes citizen requests through an Entry Agent to domain-specific agents, which access shared services for document processing, knowledge retrieval, tax computation, and payments. The infrastructure layer exposes UiPath Orchestrator capabilities and external government systems.}
\label{fig:architecture}
\end{figure}

The system state is defined as a \texttt{TypedDict} (\texttt{BaseAgentState}) that flows across all nodes and includes: the user query, conversation history with LangGraph's message aggregation reducer, routing control fields (\texttt{current\_agent}, \texttt{next\_agent}), intent classification results, workflow status tracking, and a shared context dictionary for cross-agent data exchange. The graph accepts a \texttt{GraphInput} (a single \texttt{query} string) and produces a \texttt{GraphOutput} containing the response text, detected intent, confidence score, and workflow status.

\subsubsection{Orchestration layer: Entry Agent}
\label{subsubsec:entry}

The Entry Agent serves as the sole entry point for all user interactions and implements intent detection with structured output extraction. Upon receiving a user query, it invokes an LLM (GPT-4 via the UiPath LLM Gateway) with a system prompt that enumerates the available service categories and instructs the model to classify the request. The LLM is configured with \texttt{with\_structured\_output} to return an \texttt{IntentClassification} Pydantic model containing:

\begin{itemize}
\item An \texttt{intent} field constrained to one of nine literal values: \texttt{pfa\_d212\_filing}, \texttt{pfa\_cas\_cass}, \texttt{property\_sale\_tax}, \texttt{rental\_contract\_registration}, \texttt{fiscal\_certificate}, \texttt{efactura\_b2b}, \texttt{efactura\_b2c}, \texttt{general\_question}, or \texttt{unclear}.
\item A \texttt{confidence} score in $[0, 1]$.
\item A \texttt{reasoning} string explaining the classification.
\item An \texttt{ExtractedEntities} object capturing domain-specific values mentioned by the user (annual income, property value, ownership years, monthly rent, invoice type).
\end{itemize}

A deterministic mapping (\texttt{INTENT\_TO\_NODE}) translates classified intents to graph node names. The routing function applies a confidence threshold: if confidence falls below the configured threshold, the request is redirected to a clarification node regardless of the classified intent. This two-stage mechanism---structured LLM classification followed by threshold-gated deterministic routing---ensures that ambiguous requests are handled gracefully rather than dispatched to an inappropriate domain agent.

\subsubsection{Domain agents layer}
\label{subsubsec:domain}

Five domain-specific agents handle the core tax service workflows. Each agent is implemented as an asynchronous node function that receives the shared \texttt{BaseAgentState}, invokes the LLM with a domain-specific system prompt, interacts with shared services as needed, and returns state updates including response messages.

\paragraph{PFA/Freelancer Agent.} Handles Declaratia Unica (D212) filing for self-employed individuals. The agent collects income information from the user or extracted entities, delegates to the Calculation Service for CAS (pension, 25\% rate) and CASS (health, 10\% rate) contribution computations based on minimum salary thresholds, and guides the user through the submission process via ANAF SPV. CAS is triggered when annual income $\geq 12 \times$ minimum gross salary (39{,}600 RON for 2024), computed on the threshold amount. CASS is triggered when annual income $\geq 6 \times$ minimum gross salary (19{,}800 RON for 2024).

\paragraph{Property Sale Agent.} Computes property sale tax based on ownership duration: 3\% for properties held less than 3 years, 1\% for properties held 3 years or more. The agent extracts the property value and ownership period, delegates to the Calculation Service, and provides payment guidance through Ghiseul.ro.

\paragraph{Rental Income Agent.} Manages rental contract registration with ANAF and computes the 10\% flat tax on annual rental income. The workflow involves contract data collection, registration through the SPV portal, and tax payment processing.

\paragraph{Certificate Agent.} Assists users in obtaining fiscal attestation certificates (\textit{Certificat de atestare fiscala}) by identifying the required certificate type, verifying documentation requirements, and guiding the submission process.

\paragraph{E-Factura Agent.} Supports electronic invoicing for both B2B (mandatory for VAT-registered companies) and B2C transactions. The agent handles invoice data collection, XML generation conforming to the RO e-Factura standard, submission to the national e-invoicing system, and status monitoring.

All domain agent nodes are wrapped with a response extraction function that automatically populates the output \texttt{response} field from the last AI message in the conversation, ensuring consistent output formatting. Each domain agent terminates the graph execution upon completion (edges to \texttt{END}).

\subsubsection{Shared services layer}
\label{subsubsec:shared}

Four shared services provide cross-cutting capabilities accessible to all domain agents:

\paragraph{Document Intake Service} Processes uploaded documents through OCR (via UiPath Document Understanding) and validates extracted data against document-type-specific schemas. The service supports D212 forms, rental contracts, and invoices, returning structured data with confidence scores and validation error lists. Documents with OCR confidence below 80\% are flagged for manual review.

\paragraph{RAG Service} Implements retrieval-augmented generation using the UiPath \texttt{ContextGroundingRetriever}. Each agent type maps to a dedicated Context Grounding index containing relevant portions of the Romanian Tax Code and procedural guidance. The service retrieves the top-$k$ most relevant passages for a given query, constructs a grounded system prompt with the retrieved context, and generates an answer conditioned exclusively on the evidence. This architecture ensures that tax code interpretations are traceable to specific indexed documents rather than relying on the LLM's parametric knowledge.

\paragraph{Calculation Service} Performs deterministic tax computations using Python's \texttt{Decimal} arithmetic to avoid floating-point errors in financial calculations. The service implements three computation types: PFA contributions (CAS/CASS with threshold-based eligibility), property sale tax (rate selection by ownership duration), and rental income tax (flat 10\% rate). All computations use configurable parameters (minimum salary, tax rates) loaded from application settings, enabling adaptation to annual regulatory changes without code modifications.

\paragraph{Payment Service} Integrates with Ghiseul.ro for tax payment processing. The service constructs payment requests from the shared context (amount, payment type, reference number, taxpayer identifiers), initiates the payment through the Ghiseul.ro API, and returns transaction confirmation details including a redirect URL for the citizen to complete the payment.

\subsubsection{Infrastructure layer: UiPath platform integration}
\label{subsubsec:infrastructure}

The infrastructure layer bridges the agent system with the UiPath Orchestrator platform and, through mocked boundary adapters, with the response schemas of the target government systems. Five UiPath SDK service categories are leveraged:

\begin{itemize}
\item \textbf{InvokeProcess}: Triggers attended and unattended robotic processes for operations that require browser-based interaction with government portals (e.g., SPV login and form submission).
\item \textbf{CreateTask}: Creates Action Center tasks for human-in-the-loop review when automated processing encounters edge cases, low-confidence OCR results, or complex tax situations that require expert validation.
\item \textbf{Queues}: Manages batch processing of declarations and payment requests through Orchestrator queues with built-in retry logic, priority handling, and dead-letter management.
\item \textbf{Buckets}: Provides persistent document storage for uploaded tax forms, contracts, invoices, and generated certificates through Orchestrator storage buckets.
\item \textbf{Context Grounding}: Hosts vector-indexed knowledge bases for RAG, allowing the system to search over ingested Romanian Tax Code articles, procedural guides, and regulatory updates.
\end{itemize}

The Tools Layer exposes four primary mocked tool functions that replicate the request and response schemas of the corresponding government services: \texttt{SPV\_Login} for authentication with the ANAF Spatiul Privat Virtual, \texttt{SPV\_Submit\_D212} for Declaratia Unica filing, \texttt{SPV\_Register\_Contract} for rental contract registration, and \texttt{Ghiseul\_Payment} for payment initiation. In a production deployment these functions would be replaced by UiPath robotic processes, providing resilience through the Orchestrator's built-in retry, scheduling, and monitoring capabilities.

\subsection{Fault injection layer}
\label{subsubsec:faultinjection}

\begin{figure}[t]
\centering
\includegraphics[width=\columnwidth]{PROCS_KES2026_LATEX_Template/l3pdf.drawio.pdf}
\caption{Fault injection decision flow. When an agent calls a mocked tool, the tool builds its nominal response and passes it to the \texttt{EnvironmentFaultInjector}. A seeded Bernoulli trial determines whether injection occurs: on a pass-through the original payload is returned unchanged; otherwise one of four chaos operators is selected uniformly: \emph{timeout} (raises \texttt{TimeoutError}), \emph{delay} (sleeps and returns payload), \emph{partial} (nulls one field), or \emph{corruption} (replaces one field with a sentinel). A warning is emitted to the fault log before the result is returned to the agent.}
\label{fig:finjarchitecture}
\end{figure}

Production assurance for agentic systems requires robustness not only under nominal conditions but also under the integration faults that dominate real deployments: service timeouts, partial responses, payload corruption, and communication delays~\cite{Basiri2016}. To validate this robustness without requiring live access to government portals during development, we instrument the mocked external boundaries with a controlled fault injection framework that applies chaos operators at configurable rates with deterministic reproducibility.

The framework is implemented as an \texttt{EnvironmentFaultInjector} class parameterised by a random seed $s$, a per-call injection probability $\eta \in [0, 1]$, and a maximum induced latency $\Delta t_{\max}$. At each instrumented boundary, the injector performs a Bernoulli trial with parameter $\eta$; on success, one of four operators is selected uniformly at random:

\begin{itemize}
\item \textbf{Timeout}: raises a \texttt{TimeoutError} without returning a payload, simulating a non-responsive service.
\item \textbf{Delay}: sleeps for a duration sampled uniformly from $[1, \Delta t_{\max}]$ ms and returns the original payload unchanged, simulating network or processing latency.
\item \textbf{Partial response}: selects one field from the response payload uniformly at random and sets it to \texttt{None}, simulating an incomplete service response.
\item \textbf{Corruption}: selects one field and replaces its value with a fixed sentinel string, simulating a schema mismatch or deserialisation error.
\end{itemize}

Injection is decoupled from mock implementations via a Python decorator \texttt{@with\_fault\_injection("operation")} that wraps each mock function's return value through the injector. Mock function bodies remain identical to their nominal implementations; injection is fully disabled by setting $\eta = 0$. Nineteen boundary operations are instrumented: 8 function-level tool wrappers (SPV login, D212 submission, contract registration, payment, OCR, e-invoice submission and status, certificate request) and 11 class-method wrappers across the three external system stubs (\texttt{MockANAFSPV}, \texttt{MockGhiseulRo}, \texttt{MockEFacturaSystem}). Each injected event is emitted to a dedicated logger with the operation name and operator type, enabling deterministic replay from a given seed.

\section{Evaluation}
\label{sec:evaluation}

\subsection{Prototype and experimental setup}
\label{subsec:setup}

The prototype is implemented in Python~3.11 with LangGraph~0.2, \texttt{langchain-openai} for LLM calls (GPT-4o via the UiPath LLM Gateway), and \texttt{pydantic-settings} for configuration management. All external government system calls are handled through the mocked boundary layer; no live network connections are required during evaluation.

To characterise fault injection behaviour, we executed $N = 100$ boundary-crossing calls, sampled across all 8 function-level mock tools proportionally to their invocation frequency in the five demo scenarios, under five injection rates $\eta \in \{0.00,\allowbreak\ 0.25,\allowbreak\ 0.50,\allowbreak\ 0.75,\allowbreak\ 1.00\}$ with fixed seed $s = 17$ and $\Delta t_{\max} = 250$\,ms. We classified each injected fault as \emph{detectable} if the agent's downstream response correctly indicated a failure (exception propagation, error message, or degraded-service notice), and as a \emph{silent pass-through} otherwise.

A fault is structurally silent when: 
\begin{itemize}
    \item the \textbf{delay} operator leaves the payload intact, adding only latency; or
    \item the \textbf{partial} or \textbf{corruption} operator perturbs a non-critical field so that the downstream success predicate (typically \texttt{status == "success"}) still evaluates to true, after which the LLM may generate a plausible response despite receiving a partially null or corrupted context.
\end{itemize}

\subsection{Qualitative results}
\label{subsec:qualitative}

We trace a D212 submission triggered by a citizen reporting PFA income of 150{,}000\,RON. The Entry Agent classified the intent as \texttt{pfa\_d212\_filing} (confidence 0.95) and routed to the PFA Agent, which computed CAS\,=\,9{,}900\,RON and CASS\,=\,1{,}980\,RON (total 11{,}880\,RON) before prompting for submission confirmation. On the confirmation turn, the ANAF SPV submission call was intercepted with $\eta = 1.0$, $s = 17$, producing:

\begin{center}
\small\texttt{[WARN] fault injected | op=mock\_spv\_submit\_d212 | type=partial}
\end{center}

The partial operator selected the \texttt{message} field of the \texttt{SPVSubmissionResult} dataclass uniformly at random and set it to \texttt{None}. Because the \texttt{status} field was not affected and remained \texttt{"success"}, the agent followed the success branch and the LLM generated: \emph{``Declara\c{t}ia D212 a fost depus\u{a} cu succes! ID: D212-01B66C85C3, Timestamp: 2026-03-27T22:20:32.''} The citizen received a plausible success confirmation while one field of the underlying response object was null, a silent pass-through in which the fault was neither detected nor surfaced.

This behaviour is structurally guaranteed for any partial or corruption fault that does not perturb the branching predicate: the probability of a silent pass-through for a single-field perturbation on a response object with $|\mathcal{F}|$ fields is $1 - \frac{1}{|\mathcal{F}|}$, which equals 0.75 for the four-field \texttt{SPVSubmissionResult}.

Across all non-zero injection rates, approximately 63\% of injected faults propagated silently. This is consistent with the theoretical expectation: delay faults (25\% of operators) are structurally silent; partial and corruption faults are each silent with probability 0.75, yielding an expected silent rate of $0.25 + 2 \times 0.25 \times 0.75 = 0.625$. Timeout faults (25\% of operators) are always detectable as they raise an unhandled exception. Because this silent rate is a structural property of the operator mix and the response schema, it remains stable at 63--64\% regardless of $\eta$: higher injection rates increase the absolute volume of silent faults proportionally without changing the ratio.

Delay faults introduced a mean overhead of $125.5 \pm 72.2$\,ms per affected call (theoretical mean for uniform sampling over $[1, 250]$\,ms). At $\eta = 0.50$, this corresponds to an expected per-scenario latency increase of approximately 65\,ms integrated over mock-call frequency.

These results demonstrate that a substantial majority of realistic integration faults (those affecting non-critical fields or adding only latency) are invisible to an agent that conditions its behaviour solely on a service-reported status flag. This structural gap motivates the addition of a response validation layer that checks agent outputs against formally specified contracts, independent of the service's own status indicator.

\subsection{Cost feasibility}
\label{subsec:cost}

A practical deployment consideration for public institutions is the operational cost of LLM inference. We estimate per-session costs based on the GPT-4o model (May 2025 pricing: \$2.50 per 1\,M input tokens, \$10.00 per 1\,M output tokens), which serves as the backbone of all agent LLM calls through the UiPath LLM Gateway.

A typical citizen session involves: (i)~one Entry Agent intent classification call (${\sim}2{,}000$ input tokens for the system prompt, conversation context, and intent schema; ${\sim}200$ output tokens for the structured classification), (ii)~two to three domain agent turns (${\sim}5{,}000$ input tokens per turn including the domain system prompt, accumulated conversation history, and tool results; ${\sim}500$ output tokens per response), and (iii)~one RAG retrieval-grounded generation (${\sim}3{,}000$ input tokens for retrieved passages plus query; ${\sim}400$ output tokens). This yields an estimated total of ${\sim}20{,}000$ input tokens and ${\sim}2{,}100$ output tokens per session, corresponding to a per-session cost of approximately \$0.07.

Furthermore, costs can be reduced by substituting smaller models (e.g., GPT-4o-mini at roughly one-tenth the cost) for intent classification and simple routing tasks, reserving the full GPT-4o model only for domain reasoning and RAG-grounded generation.


\section{Conclusion}
\label{sec:conclusion}

We have presented a multi-agent architecture for Romanian tax administration and a complementary fault injection framework for systematic robustness evaluation at external service boundaries. The system covers five tax service domains (PFA contributions, property sale tax, rental income, fiscal certificates, and electronic invoicing) orchestrated through a LangGraph state machine with intent-based routing, RAG-grounded domain agents, and shared services for tax computation, document processing, and payment handling. The fault injection framework instruments 19 boundary operations with four chaos operators applied at configurable rates and with deterministic reproducibility via a seeded RNG, while remaining architecturally decoupled from the mock implementations.

Empirical evaluation across $N = 100$ boundary calls reveals a structural silent pass-through rate of approximately 63\%: faults that do not perturb the branching predicate evaluated by the downstream agent logic are entirely invisible to both the agent and the citizen, even when the LLM receives a response containing null or sentinel-valued fields. This finding underscores a critical gap in the current state of agentic AI: the absence of dedicated quality assurance frameworks capable of detecting such silent failures before they reach end users. As Paduraru et~al.~\cite{Paduraru2026} argue, agentic AI systems require trace-based assurance frameworks that instrument executions as structured message-action traces with explicit contracts, enabling deterministic replay, fault localisation, and runtime governance through action mediation. Without such frameworks, the 63\% silent pass-through rate we observe would remain entirely undetected in a production deployment, potentially leading to citizens receiving incorrect tax guidance or confirmation of failed submissions.

The cost feasibility analysis further supports the viability of institutional adoption: even for a large agency processing 5{,}000 daily interactions, LLM inference costs remain under \$8{,}000 per month, a negligible fraction compared to human operator salaries.

Future work will address the quality assurance gap by integrating the trace-based contract verification approach proposed by Paduraru et~al.~\cite{Paduraru2026}, defining output contracts that specify, for instance, that a submission identifier must be non-null, that a payment code must match the expected format, and that a fiscal certificate response must include a valid download URL. Such contracts, combined with runtime governance mechanisms that can rewrite or block unsafe agent actions, would close the silent pass-through gap identified in this work. Together with the domain-specific agents and fault injection capability presented here, a trace-based assurance layer would complete an end-to-end quality assurance pipeline suitable for production deployment of agentic AI in regulated public services.
